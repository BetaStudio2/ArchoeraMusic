# 解码热循环定位报告（perf 采样）

> decode-optimization 专项**第一步**：先 `perf` 定位热循环，再对对象下刀（`decode-optimization.md` §0/§6 纪律）。
> 状态：**仅定位，未动代码**。产物：本文件 + `/tmp/p_<fmt>_<mode>_<run>.data` 原始采样（可复查）。

## 0. TL;DR

- **自检通过**：`perf stat true` 正常（`kernel.perf_event_paranoid=2`，用户态采样 OK）；taskset 可用。无权限障碍，未改动系统参数、未装包。
- 采样机为 **混合核（P+E）**，短进程在不同核间迁移会污染计数 → 全部固定到 **P 核 cpu12**（taskset）后，era 侧读数稳定（±2–5%）。
- 单流 20s 合成语料（flac / m4a(aac) / mp3），era(engine_mode=1) 与 Stable(engine_mode=0) 对照：
  - 三格式 **era 均已被 Zig 接管**（profile 中均为 `fmt.*` 热函数，输出 pcm_f32le 同长）。
  - **era 指令数 = Stable 的 2.1–3.4×**、cycles 1.6–2.0×、wall ≈1.4–2.1×（快慢次序 flac > m4a > mp3，与 SCORE 逐格式 ×RT 一致）。
  - era CPI(0.26–0.31) 反而低于 Stable(0.42–0.48) —— **era 不是跑得低效，而是指令多**：同功能译码指令约是 ffmpeg 的 2–3×。
- 每格式唯一大热区：
  - **flac**：`fmt.flac.bitreader.BitReader.readBits` 自占 ~33–36% + `io.Reader.read` ~18–22%（其中 ~14% 是 readBits 的逐字节拉取）→ **位流访问路径 ≈50%**。
  - **m4a/aac**：`fmt.aac.lib.Aac.decodeIcs` 自占 ~39%（内含 spectrum/Huffman/去量化 ~15%、readBits ~12%、scalefactor ~4%）；MDCT/IMDCT 系合计 ~11–12%。
  - **mp3**：`fmt.mp3.synth.synthGranule` ~20%（多相合成，含 dctII）+ `fmt.mp3.lib.readImpl` ~19%（Huffman/帧）+ `imdct36` ~7% + `io.Reader.read` ~11–13%；IMDCT+合成 ≈28%。
- Stable 侧 `libavcodec.so` 为 **stripped**（无符号），top 项是裸地址且单片 ≤3%（分散 + 启动/loader 噪声）→ **缺符号**，函数级对照不可做，改以指令/cycle 总量对照。

局限（务读）：
1. 每进程总时长仅 ~20–43ms，内含 **~75M 指令固定开销**（启动/引擎初始化，占 flac-era 约 12%）。perf 采样为近似，占比 ±1–3ppt。
2. 语料为**合成正弦**：残差/Rice 码与 AAC/MP3 Huffman 码表分布偏"理想"，与真实音乐不同；位读取占比可能**低估**真实曲目的 Huffman 代价。仅作定位，不作为精确性能声明。
3. cache-misses 绝对值很小（~80–130k，级别低），且 run 间抖动 ±30%，只供方向性判断。
4. Stable 侧 ffmpeg 解码**缺符号**，无法函数级对照（不重编，按文档要求记录「缺符号」）。

## 3. era 每格式 top 热函数（自占比，2 次 record 取代表值）

### 3.1 flac（差距最大 3.4×）

| 占比 | 函数 | 归类（decode-optimization §4） | 备注 |
|---|---|---|---|
| ~34% | `fmt.flac.bitreader.BitReader.readBits` | **#3 位读取/Huffman** | 内联合并 readBit + readGolombFlac + crc8Update + fetchByte；callgraph 内 readBits 本体 ~17%、readGolombFlac ~6%、crc8Update ~8% |
| ~20% | `io.Reader.read` | 公共 io 拷贝/预读 | 其中 ~14% 由 readBits 逐字节 fetchByte 触发；另有 readFile ~2%（与 decode-optimization §3.2 "io 前瞻缓存"教训吻合） |
| ~7% | `fmt.flac.subframe.decodeContent` | 预测/LPC 数学 | 残差→样本 |
| ~4.5% | `fmt.flac.residual.decodeResiduals` | 残差整形（位→值） | readGolombFlac 上层 |
| ~4.2% | `fmt.flac.lib.readImpl` | 帧头/控制 | |
| ~1.5–2.4% | `pcm.convert.toFloat` | #1 公共 convert | int→f32 |

→ flac era 的 50%+ 周期落在「位抽取 + 逐字节 io 拉取」路径（readBits+io.Reader.read 是同一链路的两层）。

### 3.2 m4a / aac

| 占比 | 函数 | 归类 | 备注 |
|---|---|---|---|
| ~39% | `fmt.aac.lib.Aac.decodeIcs` | **#3 Huffman/去量化** 为主（spectrum 解码域） | callgraph 内 decodeSpectrumAndDequant ~15%、readBits ~12%、decodeScalefactors ~4%、showBits ~4% |
| ~13% | `fmt.aac.lib.Aac.decodeFrame` | 帧/元素控制 | |
| ~4.3% | `fmt.aac.mdct.Mdct(f32).transform` | **#2 MDCT** | |
| ~5%（合计） | `Mdct(f32).fftSr__anon_*`、`fft8`（各 0.8–1.4%） | **#2 MDCT 内 FFT** | 通用分裂基 FFT（未见预计算 trig/专用 radix） |
| ~2% | `fmt.aac.lib.Aac.imdctAndWindowing` | #2 合成/加窗 | |

| ~1.7% | `libm.so llrintf32` | #4 浮点相关 | |

→ MDCT/IMDCT 系（transform+fftSr×n+windowing）合计 ≈ **11–12%**；谱解码+Huffman 域（decodeIcs+decodeFrame umbrella）≈ **50%+**。

### 3.3 mp3（era 最接近 Stable 的一档 2.1×）

| 占比 | 函数 | 归类 | 备注 |
|---|---|---|---|
| ~20% | `fmt.mp3.synth.synthGranule` | **#5/#2 多相合成 + IMDCT** | callgraph 内 dctII ~6%、scalePcm ~2%、synthPair |
| ~19% | `fmt.mp3.lib.readImpl` | **#3 Huffman/位 + granule 解码** | 本体(self) ~12%，另 huffman ~1.9%、midsideStereo ~1.5%、antialias ~1.0% |

| ~7% | `fmt.mp3.layer3.imdct36` | **#2 IMDCT**（另 imdct12 在 readImpl 内 ~0.8%） | |

→ IMDCT+合成路径（synthGranule+imdct36+imdct12）≈ **28%**；帧/位/Huffman 域（readImpl+io）≈ **31%**。

## 4. Stable 侧说明（对照，缺符号）

- `perf report` 中 Stable 的 top 函数为 **`libavcodec.so.63.1.101` 裸地址**（`0x0ec8221`、`0x03eaf9c`、`0x0d40f8`…）与 **ld-linux（动态装载/符号解析）**；单片自占比 ≤3%，工作分散。
- 原因：本地 ffmpeg 为 **stripped** release，且 Stable 运行含较多启动/加载固定开销，其解码总量本来就小。
- **结论**：函数级对照不可做，按总量（§2）判断差距规模与"era 慢在哪些函数"（§3）；若需 Stable 对照明细，需带符号重建 ffmpeg —— 不在本次范围。

## 5. 差距归因（era vs Stable，同文件同长度）

- **公共层（#1 convert 等）不是主差距**：`pcm.convert.toFloat` 仅 1.5–3%；修正 `decode-optimization.md` §3.1 的猜测 —— 真正"全格式公共地板"在**位流取数下层（io.Reader 逐字节拉取）**，flac/mp3 各被吃 ~12–20%，ffmpeg 用宽位缓冲 + 预读规避。
- **flac**：单链路 `readBits + io.Reader.read ≈ 50%`。flac 无 Huffman/变换，纯 Rice 位解码 + 线性预测 + CRC；era 逐位/逐字节小粒度拉取是放大来源（指令 3.4×）。
- **m4a/aac**：`decodeIcs/decodeFrame` 谱解码+Huffman 域 ~50%，MDCT 用通用 `Mdct(f32)`（split-radix FFT，未见预计算旋转因子/查表）~12%。aac 差距主要在 spectrum 域与变换实现层。
- **mp3**：合成与 IMDCT（~28%）+ Huffman/帧解码（readImpl self 12% 最大单项，可能含多次零跳转/掩码）+ io ~12%。era 已最接近（2.1×）。

## 6. 建议动刀顺序（perf 实证 → 对照 §4 候选；每次只动一个，过 §5 门）

> 说明：文档 §7 原排"先 #1 公共 convert"。perf 显示 **convert 实际仅 ~2%**，实证热点在 **位读取/io 取数**。建议按命中重排（纪律不变：一次一个、逐格式 wall + correctness 零回退）。

| 序 | 对象 | 依据（热区占比） | 命中 §4 | 备注 |
|---|---|---|---|---|
| 1 | **flac 位流取数路径**：BitReader 批量取位/宽位缓冲、CRC-8 与字节拉取减频（避免每 bit 触 io.Reader） | flac era `readBits`+`io.Reader.read` ≈ **50–55%**，era/Stable inst 3.38×（最大单格式差距） | #3（+公共 io） | 先验文档 §3.2 教训：flac 慢曾根因于 io 前瞻。保 lossless bit-exact 门（§5）易验证 |
| 2 | **公共 Reader 取数**：一次大块预读取代逐字节 fetch（同一改动惠及 flac io ~20%、mp3 io ~12%） | 两格式 io 合计 | 公共层 | 若 #1 已在改位读，可与 #1 联动；仍按一个 commit 一个目标 |
| 3 | **mp3 IMDCT/多相合成**：imdct36/imdct12 走快速 IMDCT + 预计算窗/三角，synth 减少每样本重复计算 | mp3 合成+IMDCT ≈ **28%** | #5/#2 | 保 `|corr|≥0.999` / ±≤1 LSB |
| 4 | **aac 谱解码域**：Huffman 批量解 + scalefactor/去量化查表（去 pow 类重复） | aac `decodeIcs/decodeFrame` umbrella ≈ **50%**（内 decodeSpectrumAndDequant ~15%） | #3 | 与 MDCT 改造可并行评估但一次一个 |
| 5 | **aac MDCT 专用化**：Mdct(f32) 预计算旋转因子/专用 radix，替代通用 split-radix | MDCT 系 ≈ 11–12%（aac） | #2 | 有损格式，守 corr 门 |

参考排期：先 1→2（flac+公共，改动集中、验证快），后 3（mp3 最大单块）→4→5（aac）。每步照 §5：无损位精确 / 有损 corr 门 + 全量 `zig build test` + scorecard 看逐格式 wall 下降方向。

## 7. 复现

```bash
# 语料（合成正弦多音，20s/44.1k/stereo）
mkdir -p /tmp/opencode/perfcorpus
ffmpeg -loglevel error -f lavfi -i "aevalsrc=0.45*sin(2*PI*220*t)+0.3*sin(2*PI*330*t)+0.2*sin(2*PI*440*(1+0.05*sin(2*PI*0.5*t))*t):s=44100:d=20" -ac 2 -c:a flac -y /tmp/opencode/perfcorpus/out.flac
ffmpeg -loglevel error -f lavfi -i "aevalsrc=..." -ac 2 -c:a aac -b:a 192k -y /tmp/opencode/perfcorpus/out.m4a
ffmpeg -loglevel error -f lavfi -i "aevalsrc=..." -ac 2 -c:a libmp3lame -b:a 192k -y /tmp/opencode/perfcorpus/out.mp3

cd app/core/audio-engine
perf stat -e cycles,instructions,cache-misses \
  taskset -c 12 ./build/archoera-audio-engine /tmp/opencode/perfcorpus/out.flac --engine-mode 1 --player-file /tmp/o.wav --no-limiter
perf record -F 20000 -g -o /tmp/p_flac_m1.data \
  taskset -c 12 ./build/archoera-audio-engine /tmp/opencode/perfcorpus/out.flac --engine-mode 1 --player-file /tmp/o.wav --no-limiter
perf report --stdio --no-children -i /tmp/p_flac_m1.data   # era；engine-mode 0 = Stable
```

> 结论仅代表**合成语料 + 本机 + 当前 ReleaseFast 内核**；真实曲目下 Huffman/残差分布不同，建议动刀前后各用 scorecard 语料（含真实格式样本）复核方向。
