# ArchoeraMusic 解码基准报告 — EraAudio(自研) vs Stable(FFmpeg)

- 日期：2026-09-04　构建快照：`relfast-23:50-snapshot`
- 引擎：`ArchoeraMusic/app/core/audio-engine/build/archoera-audio-engine`
- 内核 Zig 0.16.0 / ReleaseFast（`zig build -Doptimize=ReleaseFast` 后 `cmake --build build`）
- 语料：`/tmp/eng/`（44 个音频文件，2s–900s，含自造补充，见 §5）
- 数据：`tests/bench/data/BENCH_2026-09-04.csv`（95 行）
- 源码快照 md5：decoder.zig `423c590c`、fmt/mka/{ebml,lib}.zig `24acb18f/6190af79`、fmt/m4a.zig `54b9beec`、pipeline.c `a6677d27`（跑数期间另有代理在改 fmt/mka，23:48 后再无变更；本报告为 23:50 引擎二进制实测）

## 1. 结论速览

1. **Stable/FFmpeg 全部格式流式解码，RSS 恒定 ~37–40MB**，即使 74MB WavPack / 67MB mka 也不随文件增长；输出时长与源一致（见 §6），是可信基线。
2. **EraAudio 自研内核内存已基本流式化**：flac / wavpack(wv) / mp3 / ogg-vorbis / opus / pcm(wav) / tta / ac3 / eac3 / mp2 / adts(aac) 的 RSS 均 ~27–37MB 且**不随文件/时长增长**（实测最大 900s、74MB 文件 RSS 不变）。
3. **残余「整缓冲」只剩 mka**：`big300.mka`(33.8MB)→98MB，`big600.mka`(67.7MB)→163MB；RSS−流式基准 ≈ **1.9×容器体积，随时长成倍增长** → mka 模块把内轨解码整段 PCM 缓进内存（非逐块流式）。小 mka(2s) 正常 → 仅内容体积相关。
4. **m4a / AAC 不是整读，但工作集偏高且恒定**：native 打开任何 m4a/aac（含 64KB 的 4s 文件）即 ~46–61MB（aac_st.m4a 60.7MB、nz.m4a 60.3MB、big900.m4a 61.4MB），几乎不随时长增长 → 为固定解码器缓冲/表，非文件整读。
5. **阻塞项（CPU 无法对比的根因，非内核 bug）**：`src/pipeline.c:409` 原生分支把 `process_dsp_chain()` 的返回值当「是否继续」判定，而 `encoder_write_pcm()` 成功时返回 **0** → **EraAudio native 解码只输出 ~0.067s 就误判 EOF**。FFmpeg 分支忽略该返回故不受影响。EraAudio 的 CPU×RT 因此**目前不可测**，需先修 C 侧一处逻辑（建议见 §8）。RSS 数据不受影响（整缓冲发生在 open/首读阶段，已在早退前完成）。
6. 异常：a) 上述 native 早退；b) `zig build`（默认 **Debug**）产出的内核在 engine 中使 m4a `open` 段错误（Debug 大栈帧，build.zig 注释已记载 60MB 栈帧问题）；必须 `-Doptimize=ReleaseFast`；c) 本快照 `zig build test` 运行器中途崩溃、无 563 汇总（见 §7）。

## 2. 方法（tests/bench/，可复用）

- `bench_decode.py`：单文件×单引擎模式测量。子进程跑 `archoera-audio-engine <f> --engine-mode 0|1`，stdout 写临时 OGG/Opus；采集 墙钟(`time.monotonic`)、user+sys(`getrusage(RUSAGE_CHILDREN)`)、**峰值 RSS**(`/proc/<pid>/status` VmRSS 每 2ms 轮询)、退出码、输出字节、接管方(解析 stderr 的「接管/回退」)。
- `run_bench.py --corpus <dir> --engine <bin> --csv <out> [--reps N]`：遍历语料跑 0/1 双模式，聚合行写 CSV（流式进度到 stderr）。
- `make_report.py --csv … --md …`：由 CSV 生成 Markdown 汇总（本报告即由它+人工补注而成）。
- 用法示例：
  ```
  cd ArchoeraMusic/app/core/audio-engine
  zig build -Doptimize=ReleaseFast        # 内核（勿用默认 Debug，见 §7）
  cmake --build build                     # 重链 C 引擎（顺序：先 zig 后 cmake）
  python3 tests/bench/run_bench.py --corpus /tmp/eng \
      --engine build/archoera-audio-engine \
      --csv tests/bench/data/BENCH_2026-09-04.csv
  python3 tests/bench/make_report.py --csv tests/bench/data/BENCH_2026-09-04.csv --md /tmp/r.md
  ```

## 5. CPU×RT（解码耗时 / 源时长）

管道 = 解码→48k/2ch 重采样→限幅→Opus(128k) 编码，双端一致。**EraAudio native 段被 §6.1 C 侧早退 bug 阻塞**（实测 mode1 墙钟仅 0.016–0.064s = 启动+首块），下表 Era 栏为无效占位；Stable/FFmpeg 全时长有效（时长一致性见 §6）。

| 文件 | 源时长 | Stable墙钟 | Stable×RT(越低越快) |
|---|---:|---:|---:|
| big.flac / big.m4a / big.mp3 / big.opus / big.wav / big.wv | 120s | 0.62 / 0.67 / 0.77 / 1.12 / 0.77 / 0.92 | 0.0051 / 0.0056 / 0.0064 / 0.0093 / 0.0064 / 0.0076 |
| big300.{flac,mka,mp3,ogg,wv,m4a} | 300s | 1.97 / 1.92 / 1.82 / 1.77 / 2.27 / 1.92 | ≈0.0059–0.0076 |
| big600.{flac,mka,wv} | 600s | 3.42 / 3.32 / 4.08 | ≈0.0055–0.0068 |
| big900.{mp3,m4a,ogg} | 900s | 4.83 / 4.63 / 4.78 | ≈0.0051–0.0054 |
| 2s x.* | 2s | 0.032–0.064（含~30ms 进程启动） | 0.016–0.032 |

> Stable 端解码+编码管线约 **130–200× 实时**（×RT≈0.005–0.008），随格式而变（wv/mp3 略慢，flac/m4a 较快）。EraAudio vs Stable 的快慢在 native 早退修复前无法定论（表内 Era 数据不可解读）。

## 6. 输出完整性校验

- **Stable/FFmpeg**：对 17 个抽查文件（wav/flac/wv/tta/mka/m4a/ogg/opus/mp3/aac/adts/ac3）逐一 ffprobe 输出时长 == 源时长（误差 <0.05s，仅 opus 帧对齐常数），**全时长解码无截断**。注：Opus 输出字节数随源响度/编码器 ABR 波动（24bit 低电平源 ≈87kbps、16bit 音乐 ≈131kbps），故字节数不适宜做长度断言，以时长为准。
- **EraAudio native**：所有格式输出恒定 ≈0.067s / ~2KB → 早退 bug 的直接表现（见 §6.1）。

## 7. 异常与崩溃

1. **EraAudio native 早退（阻塞全格式全时长解码）** —— 根因在 C 侧 `src/pipeline.c:409`：
   `native_process_chunk()` 返回 `process_dsp_chain()` = `encoder_write_pcm()`，而后者**成功返回 0**（`encoder.c:260`）；原生分支把 `ret <= 0` 判为 EOF 而 break（`pipeline.c:409-415`）。FFmpeg 分支忽略该返回值（只查 `<0`），故 Stable 正常、EraAudio 每次只出 1 个 2048 帧块。gdb 验证：一次 `--engine-mode 1` 解码全程只命中 1 次 `zk_decoder_read`。
2. **m4a 崩溃（仅 Debug 内核）**：`zig build` 默认 optimize=Debug → `fmt.m4a.open` 被编译出约 60MB 栈帧（build.zig 注释已记载），engine（8MB 主栈）打开任意 .m4a 即段错误（bt：`fmt.m4a.open` prologue）。**ReleaseFast 后 m4a 不再崩**。→ 引擎内核必须以 ReleaseFast 构建。
3. **`zig build test` 本快照崩溃**：测试运行器中途被杀（log 止于 imdct/spx，无 563 汇总），疑与同源 in-flight 改动相关（mka 代理 23:48 仍在改 fmt/mka）。修复后再跑可确认 563。
4. 跑数期间检测到 fmt/mka/lib.zig 在 23:45/23:48 被并发修改；本报告全部数字对应 23:50 构建的引擎。

## 8. 残余整读建议（给流式化代理）

1. **mka = 唯一残余整缓冲格式**（优先级最高，他人正在修）：`fmt/mka` 目前把内轨解码的**整段 PCM** 收进内存（Δ≈1.9×容器体积，300s→600s 严格翻倍，与 2s 样本的 ~34MB 基座对照即知非容器固定开销）。建议改为逐 Cluster/SimpleBlock 解析、边喂内轨解码器边吐帧；seek 用 Cues/索引惰性定位。
2. **m4a/aac 固定高工作集（~46–61MB）**：不是整读，但每个播放会话凭空多 ~25MB 以上（64KB 的 4s 文件也 61MB）。建议核对 AAC 解码器固定表/缓冲（MDCT/窗长/内部 ring 等）是否过大或未按需分配；非阻塞项但影响移动端常驻开销。
3. **早退 bug（修 C 侧一行即可恢复 native 全时长解码与 CPU 基准）**：`pipeline.c` 原生分支应以 `zk_decoder_read` 返回 0 帧为 EOF 信号；建议让 `process_dsp_chain` 在 encoder 分支返回「已消费样本数」或改为在 native 循环里仅将 `ret<0` 视为错误、`0` 视为继续（对齐 FFmpeg 分支语义）。修复后 `tests/bench/run_bench.py` 一键重跑即可产出 EraAudio 真实 CPU×RT 与输出长度校验。
4. **构建顺序提醒（写入本文档供复跑）**：kernel 改动后必须 `zig build -Doptimize=ReleaseFast`（**勿用默认 Debug**）→ 再 `cmake --build build`；CMake 的「无 zig-out 现构建」分支同样应加 `-Doptimize=ReleaseFast`。
