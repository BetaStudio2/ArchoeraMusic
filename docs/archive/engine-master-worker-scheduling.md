## 1. 核心定位（先定死，避免设计漂移）

- **进程内**（in-process）模块化：单进程内 = 1 主控 + N 只读模块 + M 个常驻工作线程；
  **不使用子进程**（128 并发 ≠ 128 进程，否则回到"N 路 = N×(完整程序)"的 FFmpeg 老问题）。
- **主控 = Async**（事件驱动、非阻塞，只派发/簿记，不做解码、不持内核线程）。
- **工作线程 = Sync**（分到任务/流后，在线程内同步跑解码循环）。
- **完成即领（pull / eager-next）**：线程空闲即向主控报空闲，领下一件——并发上限天然 = 线程数，
  无中心队列积压、无 IO 过载。
- Async/Sync 为**内核二次增强（后置可选）**，不阻塞 Phase G 核心（Registry + §8.4.2 优先子项）。
- **子任务不预设种类**：既然具备 Async/Sync 能力，主控**不应预设用户会请求处理什么**——子任务采用
  统一、开放的描述，首批允许**热切解码 / 转码 / tag 解析**，可按需扩展（§2.1）。

## 2. 启动序列（用户草图 §架构.md 升级）

```
主进程启动
   │
   ▼
检查模块注册表（各 fmt/* 就绪、接管位图）      ← 对应 §8.4 Registry / §8.4.2 优先子项② 接管门控
   │
   ▼
就绪 → 主控  （Async：事件驱动，接受并发解码需求流）
   │
   ▼
收到解码需求 → 主控识别任务类别（§2.1 子任务抽象 × 格式）→ 等待空闲工作线程 → 派发
```

**主控职责**（事件驱动、非阻塞）：
1. 识别任务并选模块（两层：**任务类别** × **格式**），但**不预设用户请求种类**——见 §2.1 子任务抽象；
2. 监听工作线程**空闲消息**（Async 等待事件，不忙等）；
3. 按类别选择**热切需要的模块**（`Module`），开出/回收轻量**实例**；
4. 簿记（实例计数 + 资源上限，超限报 `error.InstanceLimit`）；
5. 全部短任务完成且无流处理 → **exit 0**。

### 2.1 子任务抽象（不预设请求种类，2026-09-08 用户决策）

主控 **不管用户会要求处理什么**；子任务为统一的任务描述（`Task { kind, format, source, … }`），
`kind` 允许任一种类，**首批支持（可扩展）**：

- **热切解码**（eager decode：完整 PCM 输出）；
- **转码**（decode → 目标编码/封装输出）；
- **tag 解析**（demux 层元数据，走 §8.4.2 优先子项①元数据快路径）。

`kind` 仅用于三件事，**不是能力子集限制**：
1. 选模块（`Module`：flac/mp3/opus…）；
2. 选**热切 / 兼容处理路径**（同一模块内按内容自适应）；
3. 定**实例生命周期策略**（tag 短任务即开即关；解码/转码长任务持续驱动）。

由此，未来新增请求类型（如扫描/响度分析）只增 `kind` 处理器，不改主控与工作线程骨架。

### 2.2 线程数 M 与实例 cap 取值（场景相关，引擎启动时配置）

**M（工作线程数）不由架构拍死，而是引擎启动参数**（`--thread <n>`），按消费方场景取值：

| 场景 | M 取值 | 依据 |
|---|---|---|
| **独立启动（CLI/批量工具）** | 由用户 `--thread <n>` 指定 | 对齐现有 `main.c` CLI 参数风格（如 `--player-file`）；让用户按机器核数/IO 决定 |
| **播放器内嵌** | **默认 1** | 播放是顺序单流，通常 1 条 Sync 解码线即够；确有叠播/并解码需求时由上层调大 |
| **scanner 批量接线（§2.3）** | 较大（核数/IO 并发上限内，先经 §8.4.2 优先子项③基准定） | 批量 tag 是"完成即领"短任务，M 决定吞吐 |

**实例 cap**：
- **短任务批量**：每线同时活跃实例 = 1 → `cap ≥ M`；
- **长生命周期流**（128 播放/HTTP 直连）：按流分配独立上限（fd/内存护栏，§5）；
- 默认保守值（如 `cap = M` 或略高）由启动参数给出，超限报 `error.InstanceLimit`（§8.4 不变量 4）。

### 2.3 消费方接线：scanner 批量 tag（Phase G 试点，2026-09-08 定稿）

**现状**：scanner 是 NativeAOT 编译的 C# 共享库（`scanner-ffi`，`scanner_scan/…`），由 Dart FFI 加载
**在进程内执行**；Dart 以 `parallelism`（对应 §2.2 的 `--thread`/M）启动扫描；元数据解析目前走
**TagLibSharp**（ScannerEngine.cs / Program.cs `ParseSingleFile`），进度经函数指针回调、结果 JSON、
SQLite C# 直写。

**接线决策（模块间直连，不经 Dart 逐文件中转）**：
- EraAudio（`libarchoera_mediaengine`，Zig/C）与 scanner-ffi **同属一个 Flutter 进程**，scanner 经
  **C ABI 直接 P/Invoke** 引擎的元数据导出（见 A/B），Dart 不参与 per-file 中继；
- **EraAudio 优先、TagLib 兜底（不抛弃）**：引擎存在且接管格式可解析 → 走引擎 `metadata`；
  引擎缺失 / 格式不支持 / 解析失败 → TagLibSharp 兜底，行为零回归；保留全局开关走纯 TagLib 供
  A/B 对照验收；
- scanner 的 M 并行循环即 §2.2"Sync 线"消费方（每 worker 同步调用引擎 metadata API）。

**A/B：新增轻量 `zk_metadata_*`（2026-09-08 倾向）**：
- 不复用 `zk_decoder_open`（其构造完整 decoder 上下文，tag 批量过重），新增 probe + 容器 tag 即走
  的只读导出：`zk_metadata_open(path/reader, *ZkMetaInfo, errbuf) → handle` / `zk_metadata_close`；
- **规避 JSON**：per-file 热路径结果用**结构化 C struct**（对齐 `kernel_bridge.h` 的 extern struct 风格：
  采样率/时长/codec/format + title/artist/album/year/… + 通用 tags 数组 `{key,value}` + 封面/歌词
  可选指针），不做字符串 JSON 编解码；JSON 仅在低频/一次性的控制面（如 scanner 整体进度）保留。

- 收益最大化场景：**扫描/批量 tag = 128 并发"完成即领"的主要来源**，也是"批量 tag 不再建 FFmpeg 实例"
  的落地载体。

### 2.4 模块间标准通讯管线（Bus）与遥测/日志（未来面板方向）

> 动机：后续要增加**系统占用面板**与**播放器日志面板**；若每对模块各自发明一套桥，扩展即失控。
> 定位：进程内**统一的模块通讯/遥测总线**，供部分（未来可扩展的）模块做标准通讯，区别于
> §2.3 的 per-file 直连 ABI（那是高吞吐低延迟路径，不走总线）。

- **总线形态（草案）**：进程内单一总线模块（C ABI 暴露注册/发布/订阅）：
  - `bus_publish(category, kind, *Event, len)` —— 模块上报结构化事件（非 JSON 逐字串）；
  - `bus_subscribe(category, cb)` / 环形缓冲 + 水位回调 —— 面板消费；
  - 模块注册表 + 主题分类：`telemetry.cpu/mem`、`telemetry.engine`（实例数/吞吐/队列深度）、
    `log.playback` / `log.scanner`（分级、环形、时间戳）；
- **消费方**：Dart 面板（系统占用、播放器日志）经薄 FFI 读取总线；同样规避复杂 JSON 语法，
  用定长 struct + 指针；
- **与 §2.3 边界**：per-file 元数据/解码走直连 ABI（低延迟，不进总线）；总线承载的是**低频遥测与
  日志/事件**，二者不混用；
- **范围控制**：首期只接 engine 与 scanner 的标准遥测/日志主题，其它模块按需扩类别，不改总线骨架。

## 3. 工作线程模型（M 个常驻，如 M=5；进程内 OS 线程）

```text
线程 t（Sync 解码线）循环：
  1) 空闲 → 向主控发送「空闲消息」
  2) 等待主控派发任务
  3) 收到任务（已按类别/热切模块选好）→ 打开实例 → Sync 处理流（Decoder.read() 循环）
  4) 处理完毕 → 释放实例 → 回步骤 1（可被派发到「其他类别」的另一任务）
```

- 每个线程同一时刻只驱动**一个实例**（短任务批量）；长生命周期流见 §7。
- 线程向主控报空闲 = 一次最小握手（必要竞态，用空闲栈/原子/条件变量实现，不做"零同步"）。

```
主控（Async，1）
 │  空闲消息 ◀─── 线程1 … 线程M   （M 常驻，如 5）
 │  派发任务 ────▶ 线程1 … 线程M
 │
 ├─ 模块 FLAC（只读表）──── 实例（线程内 Sync 驱动）
 ├─ 模块 MP3 （只读表）──── 实例
 └─ 模块 OGG/OPUS …（只读表）── 实例
```

## 5. 红线约束（多路隔离与资源护栏）

1. **模块只读、实例私有可变**：模块零可变成员；一切运行时状态在实例 ctx。
2. **内核仍不持线程**：工作线程/主控事件循环属宿主/引擎壳；`fmt/*` 与 `Decoder` 保持纯函数 Sync 语义。
3. **零拷贝边界**：Sync 直解单线程内才可能零拷贝；跨线程移交必须拷贝 packet。
4. **资源上限**：线程数 M、实例 cap、fd/内存护栏三重限制，防 128+ 路失控。
5. **实例即收即放**：短任务（批量 tag）"开→解析→关"，主控只登记不缓存。

## 6. 与 Phase G 核心/二次增强的关系

- **核心先行（§8.4.2 优先子项顺序）**：① 元数据快路径 `metadata.open()` → ② 接管门控 → ③ 并发/批量基准 → ④ 实例内存池。
- **本文件的 Async/Sync 调度 = 二次增强（§8.4.1）**：可先以"主控簿记 + 宿主 worker 池 + 纯 Sync 线"最小形态运行，
  跑通后按需引入本调度模型（Async 主控事件循环 + 空闲消息完成即领）。

---

## 7. 长生命周期流（128 播放 / HTTP 直连）与退出

- **短任务批量**：所有任务完成、无流处理 → 主控 Async → **exit 0**（草图「所有代理完成任务」）。
- **长生命周期流**：作业无"完成"事件 → 不用完成即领；改为**按流分配 + 每线持 1..K 路帧级分时驱动**
  （避免 1 流 = 1 线程的 128 线程重模型）。退出由外部 stop 信号收敛（清实例、停线程），无自然 exit 0。
- 流类别识别在此场景退化为"格式判定"（任务类别 = 长流解码）；HTTP 直连实例走 `io.Reader.callback`
  （§6.1 双路径），传输由宿主注入。
